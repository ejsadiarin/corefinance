# Recurring rules: one writer, next-due scheduling, reconcile on change

A recurring rule is a schedule; its rule entries are real `expenses` and `incomes` rows that exactly one code path writes, when they fall due in the owner's timezone. Stats, budgets, export and the coreban notes sync all read rows, so entries stay materialized. We rejected computing occurrences on read (no worker, no catch-up) because every read path would then have to expand schedules. At one user's scale that buys nothing and costs every query.

Four decisions follow from the bugs #5, #7, #8 and #9 kept hitting:

1. **One writer.** Rule entries are written only by the per-user materialize pass. The worker runs it for due rules; a rule write runs it for that rule's owner. There is no separate "create today's entry" path in the API: a second writer meant fixing the timezone (#9) and end-date (#5) logic in two places.
2. **Next-due scheduling.** Each rule stores `next_due_at`, the instant its next occurrence starts in the owner's timezone (Tuesday 00:00 Asia/Manila = Monday 16:00 UTC). The worker fills rules whose `next_due_at` has passed and moves it forward, and sleeps until the earliest one. This replaces both the hourly scan and the `materialized_through` watermark (#7): "missed while down" is simply a `next_due_at` in the past. The timezone is applied once, when `next_due_at` is computed.
3. **Reconcile on any schedule change.** Each rule entry records whether the user edited it. After any change to a rule's schedule (start, end, cadence, pause), the rule's existing entries are compared with the new schedule. Untouched entries the schedule no longer produces are skipped. Edited ones are kept and reported for review. Missing ones are left to the writer. Entries are never deleted. This replaces the end-date-only window from #5.
4. **One rules table.** Expense and income rules share one table with a `kind` column, as the review list (#8) already does. The leftover inline-rule columns on `expenses`/`incomes` (`recurring_type`, `start_date`, `end_date`) and the legacy backfill go away once production has no legacy rows.

The "what's new" review list (#8) pages by a cursor that never passes an uncommitted entry: rows carry the inserting transaction's id, and the cursor stops at the oldest transaction still in flight. `created_at` (transaction start) and a plain sequence both stamp a row before it commits, so a pass committing slowly could slip under a cursor that had already moved past it.

**Consequences**: the API's rule writes wait on a materialize pass for that user (one small transaction, under the per-user lock) instead of a single insert. The user's timezone becomes an input the writer must always have. It comes from the gateway (coregateway ADR-0005), not from corefinance's own `user_settings`, which goes away. Merging the rule tables is a migration on production data and lands before the logic changes, so those are written once, not twice.
