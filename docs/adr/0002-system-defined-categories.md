# System-defined categories; tags stay the owner's

Categories were created per owner, and production ended up with duplicates (two `food`, two `transportation` across accounts) and a mixed list. Reports need every peso in exactly one slice, which a free-form list can't promise. Categories become one fixed, system-defined list, kept separately for expenses and incomes. Tags stay user-defined, any number per budget record, and carry the context a category used to be stretched for: people, trips, one-offs (#6).

- Expense: food, transportation, gifts, subscriptions, bills & installments, personal care, entertainment, travel, government & school, shopping, communication, other.
- Income: allowance, gift, salary, reimbursement, other.

Four decisions:

1. **Fixed-id rows, not a slug column.** The system categories are rows in the existing `expense_categories` and `income_categories` tables with no owner (`user_id` NULL) and well-known ids that the Go code also names. Records keep `category_id`, and the API keeps its shape (`category_id`, `category_name`, color and icon), so the web, coreban's Feed and export need little change. We rejected a text `category` column checked like `priority`: it is cleaner, but it changes every record, rule, stats and import/export payload and ties the web's deploy to this one. Names, colors and icons are part of the system list. Owners can't create, rename or remove categories, and the API rejects category writes. Every write of a record or rule must name a system category of the right kind, or none.
2. **Unmatched categories become `other` plus a tag.** The migration maps each owner category to the system category with the same name, ignoring case and surrounding spaces. A record whose category has no match moves to `other` and is tagged with the old category's name, reusing the owner's tag of that name or creating it. Nothing an owner filed is lost, and the tag finds those records again. Import maps an export file's categories the same way.
3. **Reimbursements are not income in reports.** Income filed under `reimbursement` (money paid back, e.g. a friend's share of a dinner) is left out of every report's income: summary, trends, savings rate and 50/30/20. It is shown as its own figure next to them. Money on hand still counts it, because the money did arrive. We rejected subtracting it from expenses, which is more accurate for a shared bill, because then the category breakdown no longer adds up to total expenses unless each reimbursement also names the category it pays back. We rejected a per-report toggle as a choice the owner would make again every time.
4. **One migration.** A single goose migration adds the system rows, moves every expense, income and rule onto them, tags the unmatched ones, and deletes the per-owner rows. Between `make migrate-up` and the new deploy, the old binary still shows category names on records (the join is by id), but its category list asks for the owner's rows and comes back empty, so pickers are blank for those minutes. We accepted that over a two-release expand/contract with a fixed deploy order.

**Consequences**: the migration is not reversible. Its down migration can restore the tables' shape, but not split merged categories back apart. The settings page loses category editing and lists the fixed categories read-only. A client holding an old per-owner category id gets a 400 when it saves a record with it, and has to refetch the list.
